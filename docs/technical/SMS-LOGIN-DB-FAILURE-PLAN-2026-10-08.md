```text
Caused by: Error: getaddrinfo ENOTFOUND unqixnlxmpfpetsrmjpc.supabase.co
```

请求号：`4txpz-1791473121186-6d55888b34f3`。部署：`dpl_Cv6vZ19N73y5huzaigQR9TdALFPq`，代码提交 `3b914e42a6f27c434d46701c7e1d1b2d60fc31e3`。此部署仍是最新生产部署。

Google DNS 和 Cloudflare DNS 对该域名的 A 记录查询均返回 Status=3（NXDOMAIN）。当前写入失败的直接原因是数据库 API 域名无法解析，请求尚未到达数据库；没有证据将它归因为字段缺失、验证码长度、RLS 或唯一约束。

Supabase 2026-10-08 官方 NXDOMAIN 排障说明补充指出：暂停项目会停止提供项目 hostname，并导致 NXDOMAIN。因当前管理台会话已失效，项目是否暂停尚未确认；暂停是已证实可解释本次 DNS 现象的候选根因，仍需核对项目状态、真实 Project Ref 和删除审计记录后定案。

## 故障链条与发布遗漏

1. 当前生产后端在 send_code 中先清理过期验证码，但未检查清理错误。
2. 随后调用短信供应商；本次日志确认供应商返回成功。
3. 再清理旧验证码并插入新验证码。插入遇到域名解析失败，返回“验证码写入失败，请稍后重试”。
4. 由于缺少持久化记录，即使前端给出输入框，也不能保证这条短信可验证。

发布副本 `src/app/api/user/route.ts:242` 开始清理，`249` 附近发送，`266` 后插入；插入数据不包含本地新版流程的 type/login 挑战及发送审计协议。生产 sms-client 仍是旧阿里云 SDK、供应商生成验证码、成功后保存的实现。

上次本地 28 项测试是在主工作区新版后端上通过的；之后发布基线使用较旧的 GitHub main，仅移入前端及测试文件，没有同步新版短信后端和相关依赖。这是上次交付的遗漏。发布副本里的契约测试依赖 verifyStoredSMSCode 等新导出，但旧 sms-client 不提供；且 `.vercelignore` 排除了 __tests__，云端构建通过不能证明这些契约测试通过。应纠正之前将本地结果视为生产完整短信链路验证的表述。

上次生产 `/api/health` 仅返回静态服务状态、版本和时间，不检查 Supabase；它的 200 不能证明登录可用。部署中 /api/user、/api/session、/api/reset-password 均位于 hkg1。不过这次两个公共 DNS 都返回 NXDOMAIN，不能把切换函数区域作为域名不存在的解决办法。

## 尚未确认的事项

- 域名失效的上游原因：项目暂停、已删除、项目引用变化或服务异常，需 Supabase 管理台项目状态确认。
- 当前 CLI 缺少 Supabase 管理令牌，不能读取管理台项目状态。本地配置与线上日志指向相同的 Supabase 项目域名，本地 DATABASE_URL 的项目引用也相符；这不等于项目当前健康。
- 本地 REST 只读尝试遇到 TLS reset；只读 PostgreSQL 连接遇到 SSL EOF，均未获取表结构。因此暂不提出数据库结构迁移或改动 RLS。
- 上述公共 DNS 检查代表核查时刻，不证明域名永久失效。

## 执行方案与进展（已批准）

### 1. 恢复数据库依赖

通过管理台核实项目状态、真实 Project URL、最近暂停/删除/恢复事件，并确认该项目的数据仍在。根据实际状态恢复原项目，或纠正 Production 环境变量中相互匹配的 URL 和凭证；不先行新建项目或替换数据库。若涉及不可恢复的数据丢失或更换数据源，另行提供恢复方案。

恢复后从生产运行环境确认 DNS、TLS、认证和 verification_codes 只读查询均正常，再核查实际列定义、约束、权限。只有实际发现结构不匹配，才形成具体迁移及回退方案。

### 2. 修复短信发送和验证的完整后端流程

以实际生产提交为基线，列出短信链路所需的最小完整改动，不整份复制混有其他业务变更的 user 路由。

- 应用生成固定验证码，先持久化对应登录挑战，确认落库成功后才调用供应商发送同一码。首次写入失败直接返回服务不可用，不发送短信。
- 一并对齐 sms-client 的固定验证码参数、HMAC 存储与校验、用途隔离、验证码期限，以及登录/注册/补设密码的读取流程；禁止发生“保存哈希、校验仍用明文比较”的半升级。
- 供应商超时等结果未确认时保留已落库挑战，返回结构化未确认状态；前端仍可输入。明确发送拒绝时仅清理本次挑战，并正确处理短信冷却额度。
- 任何重试仅针对可确认安全的数据库操作，具有请求/挑战标识和幂等边界；发送短信不因结果未知自动重试。持续 NXDOMAIN 不靠重试掩盖。
- 补齐所需限流、挑战记录和审计依赖；先核实现存数据库结构，避免凭经验直接执行旧迁移。
- 移除旧后端打印完整供应商响应和明文验证码的日志，改为脱敏错误码、请求号、步骤、耗时及发送状态。

### 3. 改善故障提示和发布门禁

- 区分数据库不可用、供应商拒绝、发送状态未确认、验证码不正确及会话同步失败；失败不关闭弹窗。数据库尚不可用时不承诺“收到短信就一定能登录”。
- 增加受控的依赖就绪检查，数据库不可用时返回非就绪；普通健康检查仍只表示进程能响应。公开输出不暴露凭证和内部错误详情。
- 在同一个发布分支、同一依赖锁文件上安装、测试、构建后发布，记录提交号与部署号。依赖安装失败时不能用另一工作区的测试结果替代发布分支验收。
- 将生产认可的完整修复通过正常合并流程同步到 GitHub 生产分支，避免后续 main 自动部署又覆盖短信后端；不混入主工作区其他未验收修改。

## 验收条件

1. DNS 失败/数据库不可用：短信供应商调用次数为 0；返回可理解的错误且弹窗保留。
2. 正常写入：服务端持久化完成后才调用短信，发送值与校验值一致；正确码通过，错误码/过期码被拒绝。
3. 供应商发送结果未知：预存验证码仍有效，前端可输入且不重复发送。
4. 登录、注册、补设密码、关闭重开、会话同步失败恢复在最终发布分支上通过；真实数据库测试使用独立测试数据并受控清理。
5. 切换正式域名前确认部署中数据库可用；获准测试号码完成真实“发出—收到—输入—登录”闭环，记录请求号但不保存明文验证码。
6. 部署后再次核对生产提交、数据库依赖和账号流程；具备同一应用基线的回退部署。

注意：单独回退前端或切换 Vercel 区域无法恢复不存在的 Supabase 域名；基础设施恢复与后端流程修复需要分别验收。

## 当前执行进度

- 已实现：登录、重置密码、更换手机号的验证码均先生成并以 HMAC 写入，再发送相同的应用验证码；数据库清理/写入失败时不会调用短信供应商。阿里云显式拒绝时删除本次挑战；网络结果未知时保留挑战并返回可输入验证码的 202 状态。验证码使用加密安全随机数；短信日志不写出验证码或原始供应商响应。
- 已实现：验证码读取按用途过滤并兼容历史明文记录；新验证码通过统一 HMAC 校验。该实现要求 `verification_codes.type` 存在，部署此字段的迁移在仓库中，但生产数据库是否已应用仍待恢复后核验。
- 已验证：发布分支中的短信契约测试 7 项通过；改动文件 ESLint 无错误；改动业务源文件的独立 TypeScript 检查通过；Next.js 生产构建通过（仅使用本地临时 `SESSION_PASSWORD` 占位值）。
- 未完成：Supabase 项目状态、数据库 schema/只读访问、获准号码的短信到登录闭环，以及生产部署和 GitHub 主分支合并。当前 Chrome 的 Supabase 管理台显示登录页面，Supabase CLI 也没有访问令牌。用户登录后才能恢复原项目或确认另一安全路径；未确认前不更换数据源。
